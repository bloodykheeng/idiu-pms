# IDIU Procurement Management System: clickable mockup

Demo-stage mockup of the Procurement Management System that New Wave Technologies (NWT) proposed to
**International Development Institute Uganda (IDIU)**: a web console for IDIU staff and a supplier portal,
from budgets and supplier prequalification through requisitions, RFQs, evaluation, LPOs, delivery and
close-out.

- **Live mockup:** https://idiu-pms.vercel.app (Vercel redeploys on every push to `main`)
- **What it shows and why:** [`PLAN.md`](PLAN.md): decisions, roles, the story, every screen and its links
- **How a system is linked, and which pattern goes where:** [`PATTERNS.md`](PATTERNS.md): the front door, roles and
  sessions, dashboards, page vs dialog vs drawer, approvals in place, buttons and highlights. Read it before adding a screen.
- **One system, one front door:** a public site (Home · About · FAQs · Notices) → one Sign in for staff and suppliers (Register, Forgot password) → a dashboard chosen by who signed in: the staff console, the supplier portal, or an applicant's application status.
- **104 screens**, web only, 1920×1080: 4 public pages, sign in and forgot password, 3 registration steps, 85 in the staff console (9 personal dashboards, 5 approver's own copies of a record page) and 10 in the supplier portal; each in light and dark, plus 108 per-person sidebars.
- **Web only**, 1920×1080, light and dark mode. All names, figures, suppliers and IDs are **illustrative**;
  IDIU's name, logo, offices, projects and donors are real. Thresholds are examples until IDIU shares its
  procurement manual.

This README is for anyone, human or AI, who changes or extends the mockup. It follows the method of the
Letshego prototype (`../../letshego/mockups`).

---

## 1. How it is made

Nothing is drawn by hand. Every screen is **generated by Python** (`_src/`) as a plain **SVG** of
rectangles, paths and live text, so browsers show it and Adobe XD imports it as editable layers. The same
Python records **hotspots** (clickable rectangles and the screen each opens). `build.py` writes
`prototype.html`, one page that shows one screen at a time with invisible click areas on top.

```
_src/*.py ──python build.py──► web/*.svg + web-dark/*.svg   (the screens, light and dark)
                           └──► prototype.html              (viewer + all hotspots, embedded as JSON)
_src/combine.py ─────────────► all-screens.svg              (every screen on one canvas, for one XD import)
```

**Fonts travel inside each SVG.** Figtree, Bricolage Grotesque and IBM Plex Mono (SIL Open Font Licence)
are subset to the characters each screen uses and embedded as WOFF2, so the mockup looks identical on any
laptop or phone (a few KB per screen). The same font files measure text, so alignment is exact.

## 3. The drawing kit (`_src/kit.py`)

- `s = SVG(1920, 1080, title)`; `s.rect`, `s.circle`, `s.line`, `s.path`, `s.poly`, `s.text`, `s.para`,
  `s.icon`; `with s.g("name"):` groups (ids become XD layer names).
- **Text has a family:** `family="body"` (Figtree, default), `"display"` (Bricolage Grotesque), `"mono"`
  (IBM Plex Mono, reference numbers only). `tw(text, size, weight, family)` measures with the real font.
- **Components:** `chip`, `status_chip`, `button`, `field`, `select`, `checkbox`, `radio`, `toggle`, `avatar`,
  `table`, `progress`, `card`, `logo`.
- **Vocabularies** at the top of `kit.py`: palette tokens, `STATUS` colours, stage names. Change them there
  and every screen follows.
- **Screens and keys:** a screen's key is its function name before the first underscore (`w13b_scoring` → `w13b`), or an explicit `fn.key` for a person's own screen (`w01-ruth`).
- **Hotspots:** `s.link(x, y, w, h, "w11")`. Special targets: `"!theme"` (light/dark), `"!tab:w11b"` (switch a
  tab without adding a Back step), `"!back:w10"` (back to where you came from, falling back to `w10`).
- **Soft cards:** with `s.soft = True`, white cards drawn with `stroke=LINE` and `rx >= 10` get a soft
  shadow instead of a border.

## 4. Screens, keys and the build

Every screen is a function `wNN_name` returning an `SVG`; the part before the first underscore is its
**key** (`w13b_scoring` → `w13b`). Each module has a `SCREENS` list; the viewer orders screens by key, the public
site (w80–w83) first.

**Key ranges:** w80–w83 public site · w00, w00b sign in · w01–w63 staff console · w70–w70c registering · w70d and
w71–w77b supplier portal. **Areas:** every frame sets `s.meta["area"]`: `public`, `auth` (sign in, register),
`staff` or `supplier`. The viewer and the checks read it.
The full list, with what each links to, is in [`PLAN.md` §6](PLAN.md#6-screens-and-links).

```
cd _src
python build.py              # rebuild every screen + prototype.html
python build.py --png        # also render PNGs into _previews/ (headless Chrome)
python build.py w11 w30      # rebuild only matching screens (does NOT rewrite prototype.html)
python combine.py            # rewrite all-screens.svg
python check.py              # structural checks (must pass)
python smoke.py              # click through it in a real browser (must pass)
```

**Renaming a screen changes its file name.** Delete the old SVG from `web/` and `web-dark/`.

## 5. The viewer (`PROTO` in `build.py`)

- One screen scaled to the window; hotspots are percentages, so they stay aligned at any size.
- `#w11` in the URL opens that screen, also on a page that is already open; **no hash opens `w80`, the public Home**.
- Click empty space to flash the hotspots; **H** keeps them visible; `?show` turns them on.
- **Web dashboard** (one button) jumps to the front door: the public Home (w80).
- **Keys:** ← → previous/next · **F** full screen (the bar comes back when the mouse touches the bottom edge) · **D** dark mode · **Esc** exit.
- The moon button in the console's top bar switches every screen to dark (remembered in the browser).
- **Sessions:** signing in as someone (or opening one of their own screens) starts their session; the bar shows "Signed in: …". Staff and suppliers alike: a supplier's portal screens are all the company's own (`owner`). On shared console screens the viewer lays the person's sidebar and name over the screen (`chrome/`) and hides hotspots to another account's own screens or to menus their role lacks. The public site and sign in end the session. The sign-out button returns to Home; clicking the name returns to Sign in to switch. Rules: `settle()` and `allowed()` in `PROTO`.
- **A person's own copy of a record:** if `<key>-<person>` exists, a link to `<key>` opens it for that person (`resolve()`): Samuel opening the Mpumudde application gets `w21c-samuel`, with his decision.
- **Forms** (`meta.write`) open only for the roles listed; **dialogs and drawers** (`meta.modal`) dim the person's sidebar with the page (CSS filter; a drawer clips it to the sidebar) and nothing under the backdrop is clickable.
- Loads every screen up front; the bar shows "✓ Offline-ready" when done.

## 6. Testing: run both before every push

**`python check.py`** builds every screen in memory (and every person's sidebar) and fails on:
- a hotspot that opens a screen that doesn't exist;
- a screen with no area (public, auth, staff, supplier);
- signed in as any of the 9 people or 2 supplier accounts, a click that reaches another person's or company's own screen or a menu their role lacks, or a shared screen with no sidebar for them;
- a menu entry (staff or supplier) that opens no screen of theirs: nothing visible in a menu is dead;
- a form the Auditor could open; a dialog with hotspots under its backdrop or no way out;
- a list whose highlighted row opens nothing, or opens one person's own screen (the presenter's cue must be clickable for everyone who sees the list);
- the door: a public page without Sign in; Home, Sign in or Notices without Register; Register without Sign in; Sign in missing any account's dashboard; a new applicant unable to follow their application;
- a screen that can't be reached by clicking from the public Home;
- text drawn over other text on the same layer (a dialog's text is a layer above the page);
- text or hotspots outside the canvas;
- a hotspot buried under another that opens something else;
- a screen file missing from `web/` or `web-dark/`.

**`python smoke.py`** serves the repo over HTTP like Vercel and drives Chromium with Playwright:
- every screen loads (light and dark);
- every screen shows exactly the hotspots whose targets exist;
- no hash opens the public Home;
- forms: the Auditor sees no hotspot to Add user, New requisition or New budget; nor does the Country Director to New budget (Finance prepares, he approves);
- under a dialog (Ruth on w50b) the sidebar is dimmed and has no hotspots;
- full screen: hovering the public footer's links doesn't raise the bar; the very bottom edge does;
- 13 walkthroughs (`WALKS`, one through every setup list's New dialog) click real hotspots: the public site → register → application status; Home → Sign in → each staff person's path; the full supplier portal (RFQ, quote, LPOs, payments, profile, documents, renew); the applicant; signing out returns to Home. Every click must land on the expected screen, and the signed-in account and its sidebar must not change;
- the D key and the moon button switch themes;
- there are no JavaScript errors.

A new screen gets a step in a walk.

Both found real bugs while the mockup was built: a document list running off the screen, a reference line
over a page title, stacked hotspots, portal links pointing at another company's screens, and a viewer that
ignored `#key` links on an open page. Look at the PNGs too (`build.py --png`): the checks catch structure,
not taste.

## 7. Rules that keep the story consistent

- **One procurement file per purchase.** Requisitions, RFQs, Evaluations, LPOs and Deliveries are lists of
  the same files; a row opens the file (at the right tab), never a disconnected page.
- **File stages:** Requested → Approved → Sourcing → Evaluation → Award → LPO → Delivered → Paid → Closed.
- **Approvals:** Draft → Pending approval → Approved/Active/Issued; Return and Reject need a reason; the maker
  never decides; approved records change only through a revision. Steps per record are in `data.py`
  (`WORKFLOWS`) and must match w62.
- **Budget arithmetic:** Budget − Reserved − Committed − Spent = Available, computed in `data.py`; never type a
  budget figure into a screen by hand.
- **Master data is created in order** (PLAN §4) and is deactivated, never deleted, once used.
- **Each role sees only its menu** (`PERMS` in `data.py`, also drawn on w61): one role per person, named as in the proposal (§15); the System Administrator sees all 26 entries, the Auditor all but My approvals.
- **The signed-in person never changes on a click.** A screen that shows one person (their dashboard, inbox, decision, form) is built with `console(..., viewer, owner=True)`; everything else is shared and built as the System Admin (`viewer="ivan"`). Dashboard and My approvals go to the person's own (`data.menu_target`). `check.py` walks every session and fails otherwise.
- **Today is Mon 12 Oct 2026.** PR-2026-0087 (10 laptops, Kasese ICT Hub) is the flagship file; its dates in
  PLAN §2 are the truth for every history, approval and audit entry.
- **No payments, stores or mobile app** in the system (PLAN §1).
- **Never link to a screen that shows someone else.** If no screen exists for a button, it stays unlinked
  ("Download PDF", "Export") rather than open a wrong one. A **create or edit** button always opens its form, as a
  `write` screen shared by every role that may use it (`shell.writes`), never one person's own draft.
- **A record opens as a page inside the menu it came from**, with `shell.approval_panel` (timeline + who it waits
  on) for everyone and `decision_panel` on the approver's own copy `<key>-<person>`. **Dialogs only for small forms**
  (setup lists, users, a financial year), never for records like applications, revisions or budgets.
- **The demo sign-in lists accounts in the order the work flows** (who sets up, starts, approves, owns, receives,
  audits): keep that order when adding a person.
- **Highlight the row to click:** `data_table(..., hl=links.index(target))` with a shared target. **Menu entries are never unlinked:** a menu
  shows only what has a screen (a pending applicant sees only My application).
- **One front door.** Public site → Sign in (or Register) → the dashboard of whoever signed in. A new entry point
  (a page, a role, a supplier account) goes through it: add the account to the demo "sign in as" on w00
  (`public.py`) and to `data.SUPPLIER_ACCOUNTS` / `SESSIONS`.
- **One role per person.** The Evaluation Committee Member is a role (Esther, Brian, Moses) whose menu is Dashboard and
  Evaluations; membership of a committee is appointed per procurement with a declaration. Committee members don't
  raise requisitions (Harriet Kyomuhendo, a Requesting Officer, raised PR-0084 to PR-0095). Role names come from
  `data.ROLES`; use `data.ROLE_SHORT` where a name is too long.

## 8. Visual style

Light, restrained, one strong accent, built from IDIU's identity (not their old website):
sage canvas `#F3F6F2`, white cards with soft shadows, forest ink `#102A1E` text, **field green `#1A683F`**
for actions, mint `#4EAE8B` for progress, fresh lime `#D9F0B8` for "your turn" and the current stage, amber
for waiting, red only for rejected. Bricolage Grotesque for titles and big figures, Figtree for everything
else, Plex Mono for reference numbers. Signature: the **file track**; supporting: the **budget bar**.

## 9. Environment

- **Windows**, Python 3 with Pillow and fontTools (`pip install pillow fonttools brotli`); Playwright for
  `smoke.py` (`pip install playwright && playwright install chromium`).
- PNG previews use headless Chrome at `C:\Program Files\Google\Chrome\Application\chrome.exe`.
- **Vercel:** framework "Other", no build command, output directory = repo root. Generated files are
  committed; Vercel never runs Python. `.vercelignore` keeps `_src`, `.claude`, `_previews` and the docs private.

## 10. Adobe XD

File → Import → `all-screens.svg` (or any single SVG). XD needs Figtree, Bricolage Grotesque and IBM Plex
Mono installed to show the same type (the files are in `_src/fonts/`). XD edits are lost on regeneration;
lasting changes go in the Python.
